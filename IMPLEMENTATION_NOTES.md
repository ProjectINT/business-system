## Решения по неоднозначностям (вопросов не задавали)

- `cash_held_idr` есть в схеме, нет в тексте: `pending`-платежи плюс полученные платежи броней на `hold` — деньги известны, вилле не подтверждены (ТЗ 11, 4D).
- `total` — сумма по `report_months`; ночь или платёж вне окна — `OUTSIDE_REPORT_MONTHS`, видны в `trace`. Иначе итог не сходится с месяцами и виллами.
- Платёж брони на `hold` → `cash_held_idr`, `PAYMENT_HELD`: бронь найдена, значит не `unmatched`; кэш без начисления по ошибочной записи — неверно.
- `cancelled` в ТЗ не описан → `UNKNOWN_STATUS`, `hold` (ТЗ 14). Принимаются `confirmed` и `modified`.
- `action` всегда `hold`, как в примере схемы: строка `exceptions` значит «сумма не вошла в подтверждённые итоги».
- Равное `updated_at`: одно содержание — одна версия (меньший `source_event_id`); разное — `AMBIGUOUS_VERSION`. Сравнивается момент времени, не строка.
- Один `source_event_id` с разным содержанием — `CONFLICTING_EVENT`, бронь на `hold`; один `payment_id` с разной суммой — `CONFLICTING_PAYMENT`, сумма никуда не кладётся.
- Отрицательная или дробная сумма, невозможная дата, `rate_bps` вне 0–10000 — ошибка формата (код выхода 1, путь к полю), не исключение: по ТЗ 1 корректная сумма — целые рупии.

## Повторный импорт

Три ключа, одинаковые в адаптере и в базе: событие — `source_event_id` + хэш содержания (та же пара → одна запись; тот же id с другим содержанием → конфликт на разбор, не перезапись); бронь — `reservation_id` + наибольший `updated_at` (старые версии — `superseded` в `trace`); платёж — `payment_id` + хэш. В Postgres это уже устроено: файл с тем же sha256 пропускается; сырая строка всегда дописывается в `raw_record` с `row_hash` (аудит), в основную таблицу попадает один раз — тот же ключ и хэш → версии нет, другой хэш → версия n+1 в `record_version` со ссылкой на строку источника; действующий снимок даёт `eff_reservation`. Добавить: таблицу `reservation_event` (ключ `source_event_id`, `updated_at timestamptz`) и `status` платежа; конфликт версий — случай `decide` в `review_decision`.

## Перенос в PostgreSQL при живых Google Sheets

Целевая система — Supabase Postgres (ближайший регион Сингапур; масштабируется без своей инфраструктуры) и это же приложение Next.js на Vercel. Около 50 $ в месяц; при малой нагрузке укладывается в бесплатные лимиты — 0 $. Расчёт остаётся в TypeScript: одна реализация с полным покрытием работает и с JSON, и с базой — `lib/nightly` читает снимки из `eff_*` вместо файла.

1. Листы, которые люди заполняют руками, не трогаем — это источник. Рядом — синхронизируемые копии, в которые пишет только система; люди в них не правят. У каждой ячейки один автор — это защищает от потерь и дублей.
2. В систему: триггер Apps Script (по расписанию или при правке) отправляет строки в импорт → `raw_record` + `row_hash` и ключи выше. Повтор дублей не создаёт, сырые строки не удаляются.
3. Из системы: триггер Postgres (webhook) обновляет копию — проверенные данные и помесячный отчёт в привычном виде.
4. Две системы работают параллельно, отчёт сравнивается с листами по месяцам и виллам. После двух месяцев совпадения до рупии ввод переводится в систему; листы остаются архивом или отключаются — уже не существенно.

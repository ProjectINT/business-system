Статус: v1.1 от 2026-10-27, **сделан 2026-10-27, дифф без коммита** — шаги 0–10, кроме проверки на ширине 390 px (v1.1: отдельный роут со встроенным JSON, расчёт на сервере, без загрузки файлов). Сданный CLI и `results_public.json` не меняются.

## 1. Цель

Финальное задание сделано без интерфейса: ТЗ прямо просило не делать дашборд. Сейчас в нём видно только итоговый JSON. Страница показывает тот же расчёт глазами человека и отвечает на пять вопросов:

| Вопрос | Где на странице | Чем |
|---|---|---|
| Как получились цифры | Поток записей, таблица цифр | счётчики «строк в файле → в цифрах», расшифровка каждой клетки |
| Какие события вытеснены | Лента событий | лестница версий брони, дубли стопкой, что изменила новая версия |
| Из чего сложились цифры | Календарь ночей, таблица цифр | ночь × ставка × комиссия, платежи по дате, выделение ночей и платежей клетки |
| Какие бывают ошибки | Каталог исключений, значки на записях | 13 кодов в трёх видах, знаки правил DQ, сколько денег вне итогов |
| Как решить спорное | Разбор | выбор одной из пришедших версий, влияние на цифры до выбора, комментарий |

Без решений человека цифры страницы равны `results_public.json` до рупии; страница это проверяет и показывает отметкой в шапке.

## 2. Решения

1. **Роут `/events`, пункт `Events` в меню**, заголовок страницы Events visualization. Страница стоит отдельно: не вызывает `dataSource()` и `todayInBali()` (в `lib/nightly` нет текущей даты), не зависит от CSV, проверок DQ и их кэша. Отвергнуто: вкладка раздела Import — у раздела общий заголовок «· CSV» и общий источник, а здесь импорта нет.
2. **Вход — встроенные JSON-файлы**, импортированные статически (`resolveJsonModule` в `tsconfig.json` включён): файл попадает в сборку, на Vercel не нужно читать диск. Два кейса, переключение через `?case=`:
   - `final-test/case_public.json` — по умолчанию, ровно то, что сдано;
   - `final-test/variants/all-exceptions.json` — демонстрационный (шаг 2). Нужен, потому что в публичном кейсе 3 кода из 13 и ни одного спорного значения: без второго файла каталог ошибок наполовину пуст, а разбору нечего решать.

   Отвергнуто: загрузка своего JSON — нужна была бы только для проверки на чужих данных, это уже делает CLI.
3. **Считает сервер**, как на `/import/data-quality` (`dataQualityOf` на сервере → `DataQualityView` в клиенте): серверный компонент страницы вызывает функции `lib/nightly`, переводит суммы в числа через `toView` и отдаёт готовую модель клиентским компонентам. В браузер не уходят ни zod, ни `lib/calc`. Отвергнуто: расчёт в браузере — он нужен был только для загрузки файлов.
4. **Страница читает расчёт, а не считает заново.** `lib/nightly/explain.ts` строит модель из `parseCase`, `selectSnapshots` и `buildReport`. Сам он только раскладывает строки входа по id, чтобы сказать, какая копия — дубль; содержание сравнивает функцией `contentKey` из `snapshots.ts` (сейчас не экспортируется — добавить `export`, больше в адаптере ничего не меняется). Тесты связывают модель с отчётом: сумма вкладов = клетка, судьбы строк = счётчики `dedup`, отчёт модели = `runCase`. `explain.ts` не экспортируется из `lib/nightly/index.ts`, поэтому CLI и архив `nightly:pack` остаются прежними.
5. **Виды ошибок — по VALIDATION_PLAN.md 6.1**, по действию системы. Знак кода — знак сопоставленного правила DQ из `rule-meta.ts`, цвет — `ACTION_COLOR` этого действия: человек учит знак один раз на обеих страницах.

   | Вид | Коды | Что делает страница |
   |---|---|---|
   | **Решить** — спорные значения (`decide`) | `AMBIGUOUS_VERSION`, `CONFLICTING_EVENT`, `CONFLICTING_PAYMENT` | разбор: выбрать одну из пришедших записей |
   | **Исключено — исправить в источнике** (`exclude`) | `UNKNOWN_PROPERTY`, `CURRENCY_MISMATCH`, `INVALID_STAY`, `NO_COMMISSION_RULE`, `AMBIGUOUS_COMMISSION_RULE`, `UNKNOWN_STATUS`, `UNMATCHED_PAYMENT` | показывает, каких данных не хватает («нужен утверждённый курс USD», «правило V04 на 10–11 ноября»); кнопки нет |
   | **Ждёт или вне окна** (`info`, `hold`) | `PENDING_PAYMENT`, `PAYMENT_HELD`, `OUTSIDE_REPORT_MONTHS` | только показывает; `PAYMENT_HELD` берёт вид своей брони: ждёт решения или исключён вместе с ней |

   Отвергнуто: кнопка «Принято к сведению» у исключённых — в `app.review_decision` у неё нет пары и на цифры она не влияет; ввод значений в разборе (курс USD, новое правило, привязка P404 к другой брони) — решение выбирает, каким записям верить, но значений не меняет (`review_decision.sql`); `AMBIGUOUS_COMMISSION_RULE` как спорное — по решению 2026-10-27 (MONEY_MODEL_PLAN.md 2.2) пересечение правил снимается закрытием старого правила, то есть в источнике.
6. **Решение — выбор среди пришедших записей, применённый к входу.** `applyDecisions(case, decisions)` убирает из входа невыбранные версии или копии, дальше тот же `runCase`. Поля — как у `app.review_decision`: `case_key`, `record_key`, `decision: 'pick'`, выбранный `source_event_id` или отпечаток копии, отпечаток набора кандидатов (аналог `row_hash`), обязательный `comment`, `decided_by` (Finance team, как в меню), `decided_at`. Решение действует, пока набор кандидатов тот же; иначе оно «устарело», не применяется и показывается отдельно. Решения хранятся в адресе (`?case=…&d=…`): сервер читает их из `searchParams` и считает с ними; переживают перезагрузку, ссылкой можно поделиться. Встроенный JSON не меняется никогда. Отвергнуто: `localStorage` — не передать ссылкой, сервер его не видит; таблица `review_decision` — база не подключена (фаза 8); запись в файл — на Vercel файловая система только для чтения; ключ `--decisions` у CLI — ТЗ просит результат без решений.
7. **Цифры показываются с решениями**, рядом — разница с «как посчитано» (это вывод CLI); переключатель показывает исходные цифры. Без решений две версии совпадают, и разницы на странице нет.

## 3. Страница

Сверху вниз: шапка, поток записей, цифры, календарь, лента событий, исключения и разбор. Выделение общее: клик по клетке цифр, ночи, событию или коду подсвечивает связанные записи во всех разделах; строка над разделами говорит, что выделено, и снимает выделение. Выделение — состояние клиента, без запроса к серверу.

### 3.1 Шапка и поток записей

```
Events visualization                              [ Public case | All exception types ]
FINAL_VILLA_2026_PUBLIC_A · report months 2026-11, 2026-12 · final-test/case_public.json
✓ Same as final-test/results_public.json

Events    5 rows → −1 duplicate → 4 versions → −1 superseded → 3 bookings → −1 excluded → 2 in figures · 6 nights
Payments  5 rows → −1 duplicate → 4 payments → received 2 · 6 380 000 | held 1 · 50 000 | unmatched 1 · 100 000
```

- Отметка «Same as results_public.json» — у публичного кейса без решений: сервер сравнивает отчёт `runCase` с файлом, встроенным так же статически. С решениями — «With N decisions, differs from the CLI output».
- Поток — не график, а строка шагов на CSS: числа малые, разница между шагами важнее формы. Клик по шагу выделяет его записи.
- Ниже — контрольные суммы, как карточка Control totals на `/import/data-quality` (`ControlTotals` в `data-quality-view.tsx`): события — строк в файле = выбрано + вытеснено + дубли + спорные; платежи — сумма файла = поступило + удержано + не привязано + дубли + без суммы (спорные). Ни одна рупия не уходит молча.

### 3.2 Цифры: как получились и из чего сложились

```
               Accommodation    PBJT     OTA fee   Mgmt fee   Owner est.   Cash received
2026-11           2 200 000   220 000   330 000    374 000    1 496 000      2 200 000
  V01             2 200 000   220 000   330 000    374 000    1 496 000              0
  V02                     0         0         0          0            0      2 200 000
2026-12  …
Total             6 400 000   640 000   660 000  1 014 000    4 726 000      6 380 000
Not in the totals: held 50 000 · unmatched 100 000
```

- Строки — месяцы `report_months`, под каждым виллы, внизу итог: та же сетка «вилла × месяц», из которой собран отчёт (FINAL_TEST_PLAN.md 3.3). Таблица, а не график: шесть показателей разного смысла на одной оси дали бы ложные сравнения.
- **Каждая клетка раскрывается.** Наведение — список вкладов и сумма, как в `figure-sources.tsx`: «V01 · 2026-12 · Mgmt fee = R101 1 Dec 1 100 000 × 20 % = 220 000 + R101 2 Dec 220 000 = 440 000». Owner estimate — формула из клеток строки: 2 200 000 − 330 000 − 440 000 = 1 430 000. Cash received — платежи с датой: «P101 · 7 Dec · 4 180 000 = 4 400 000 + 440 000 − 660 000». Клик закрепляет выделение: ночи и платежи клетки подсвечиваются в календаре.
- Тело подсказки (`SourcesBody`: строки, «ещё N записей», итог, примечание) вынести из `figure-sources.tsx` в `components/shared/sources-body.tsx` и использовать в обоих местах; вид дашборда не меняется.
- **Состав проживания** — горизонтальная полоса на месяц и на итог: Accommodation = Mgmt fee + OTA fee + Owner estimate (ТЗ 8), три сегмента в первых трёх категориальных цветах палитры с подписями; PBJT — отдельной полосой рядом, штриховкой, с подписью «liability to the state, not income». Если owner estimate где-то отрицателен, полоса не рисуется (часть больше целого), остаётся таблица.
- С решениями: у изменившихся клеток — разница со знаком (`idrSignedCompact`), переключатель «With decisions / As computed».

### 3.3 Календарь ночей: начисление по ночам, деньги по дате

```
              Nov 28  29  30 │ Dec 1   2   3  …  7  …  10  11  12  …  15  16
V01  rules     ───── 17 % ───│───────────── 20 % ─────────────────────────────
     R101              ■   ■ │   ■   ■            ●P101                ○P303
     R303                                                              ▨   ▨  [CUR]
V02  rules     ──────────────────────── 10 % ──────────────────────────────────
     R202       ●P202                                ■   ■
No booking                                                    ●P404 → R999 [LinkSlash]
```

- Ось — дни `report_months` (61 день, около 18 px на день), граница месяцев — вертикальная линия. Строки — брони по виллам, над виллой — полоса её правил комиссии со ставками. Сетка на CSS grid, как ночи в `case-list.tsx`; на узком экране — горизонтальная прокрутка внутри карточки.
- **Ночь** — клетка, цвет — ставка этой ночи: порядковая шкала одного синего оттенка по разным ставкам кейса (у публичного 10, 17, 20 %), шаги из sequential-шкалы палитры dataviz, проверенные валидатором в тёмном режиме с `--ordinal`. Подпись ставки — в полосе правил, не в клетке. Подсказка ночи: проживание, PBJT, OTA fee, правило (вилла, даты), комиссия формулой; если HALF_UP округлил — точная дробь и результат (1 100 050 × 17 % = 187 008,5 → 187 009).
- **Платёж** — кружок на дате платежа в строке своей брони: заполненный — поступило, пустой — удержано (`pending`, бронь вне цифр), «×2» — повтор, учтён один раз. Платёж без брони — в нижней строке «No booking» со знаком. Так видно ТЗ 7: P202 пришёл 28 ноября за декабрьские ночи R202, P101 — 7 декабря за ночи 29.11–02.12.
- **Бронь вне цифр** — клетки её дат штриховкой с контуром цвета действия и знаком кода, без сумм (у R303 суммы в USD, рядом подпись «USD 10 000, not converted»). Ночи вне `report_months` — стрелка у края оси с числом ночей и знаком `OUTSIDE_REPORT_MONTHS`.
- Если вытесненная версия брони имела другие даты, её даты — пунктирным контуром в той же строке: видно, что поменяла новая версия.
- Клик по брони открывает карточку брони (3.4).

### 3.4 Лента событий: что вытеснено и почему

```
R101 · V01                                               in figures
 ┌ E_R101_V1  ×2 ───────────┐           ┌ E_R101_V2 ───────────────┐
 │ 19 Nov 09:00 UTC         │ replaced  │ 20 Nov 08:00 UTC         │
 │ confirmed · 29 Nov→3 Dec │ ────────▶ │ modified                 │
 │ 4 000 000 / 400 000 /    │    by     │ 4 400 000 ▲ / 440 000 ▲ /│
 │ 600 000                  │           │ 660 000 ▲                │
 │ Superseded · 1 copy dup. │           │ Clean                    │
 └──────────────────────────┘           └──────────────────────────┘
R303 · V01                                               excluded
 ┌ E_R303 · [CUR] USD 10 000, not converted · Excluded ┐
```

- По брони — колонки версий слева направо по `updated_at`; побеждает правая колонка (ТЗ 10). Версии с одинаковым `updated_at` стоят в одной колонке друг под другом: одинаковое содержание — одна версия (меньший `source_event_id`, решение 4.6), разное — `AMBIGUOUS_VERSION`, обе карточки спорные. Правило читается по картинке: «две разные карточки в правой колонке — система не знает, какая последняя».
- Точные копии события — стопка карточек «×2 identical, counted once» (ТЗ 9). Копии одного `source_event_id` с разным содержанием — стопка раскрыта, различающиеся поля выделены, знак `CONFLICTING_EVENT`.
- Судьба карточки — чип из `STATUS_META`: Clean (выбрана, в цифрах), Excluded (выбрана, но не прошла проверки), Pending (спорная, ждёт решения), Duplicate, Superseded; плюс Rejected — не выбрана человеком. Палитра и подписи уже знакомы по `/import/data-quality`.
- В карточке версии — что изменилось против предыдущей (поле, было → стало); у R101 — три суммы и статус.
- **Карточка брони** (Drawer справа, как `record-drawer.tsx`): версии; выбранный снимок; таблица ночей (дата, месяц, проживание, PBJT, OTA, ставка и правило, комиссия формулой) с итогом по месяцам — это `trace` отчёта в развёрнутом виде; платежи брони и куда ушли их деньги; исключения и решение, если было. **Карточка платежа** — копии, вид денег и почему.

### 3.5 Исключения: каталог и список

- **Каталог** — все 13 кодов, сгруппированные по трём видам (2.5), включая те, которых в кейсе нет (приглушены): знак, название словами, сколько записей, сколько денег вне итогов, «что исправит» одной строкой. Тринадцать классов — таблица, а не цвета на графике. Клик по коду — фильтр списка и выделение записей в календаре и ленте.
- **Список** — запись, код, деньги вне итогов и где они сейчас (удержано, не привязано, нигде), состояние: открыто / решено (кем, когда, комментарий) / решение устарело.
- Знаки (`components/events/exception-meta.ts`): у кода с правилом в `rule-meta.ts` — знак этого правила (`Layers` DQ-02, `House` DQ-04, `LinkSlash` DQ-05, CUR DQ-06, `Percent` DQ-17, FMT DQ-03, знак DQ-25 после 6b); `UNKNOWN_STATUS` берёт правило по типу записи (бронь — DQ-03, платёж — DQ-25). У `OUTSIDE_REPORT_MONTHS` правила нет — собственный тег. ID правил на экран не выводятся (VALIDATION_PLAN.md: «интерфейс показывает значком»).
- На публичном кейсе: R303 `CURRENCY_MISMATCH` (исключено, нужен курс USD), P303 `PENDING_PAYMENT` (удержано 50 000), P404 `UNMATCHED_PAYMENT` (не привязано 100 000, нужна бронь R999). Спорных значений нет — блок разбора пишет «Nothing to decide in this case» и ссылку на второй кейс.

### 3.6 Разбор спорных значений

```
AMBIGUOUS_VERSION · R404 · V02 · two versions at 25 Nov 10:00 UTC
                   E_R404_A        E_R404_B
check_out          2026-12-22      2026-12-23     ← differs
accommodation      3 000 000       4 500 000      ← differs
If chosen          Dec accommodation +3 000 000   +4 500 000
                   Dec mgmt fee        +300 000     +450 000
                   P4040 held → received            same
Comment (required) [ ……………………………………………………… ]
                   [ Use E_R404_A ]  [ Use E_R404_B ]
```

- Открывается из списка исключений и из ленты. Кандидаты рядом, различающиеся поля выделены.
- Влияние каждого варианта сервер считает заранее, вместе с моделью: `explainCase(case, [...decisions, вариант])` против текущего отчёта — изменения клеток (только ненулевые) и деньги, которые переходят из удержанного в поступившие. Данных мало, это десятки миллисекунд.
- Без комментария кнопки неактивны. Выбор добавляет решение в `d=` (`router.replace` без прокрутки и без новой записи истории), сервер пересчитывает страницу. Запись в списке — «решено», цифры и лента пересчитаны, есть «Undo». Журнал решений — под разбором: кто, когда, что выбрано, комментарий, итог влияния.
- Решение может открыть новый спор: выбранная копия конфликтного события может совпасть по `updated_at` с другой версией. Спорные случаи считаются заново после каждого решения, решения применяются по порядку.

## 4. Код

```
app/events/page.tsx     сервер: ?case=, ?d= → explainCase → toView → EventsView
components/events/
├─ cases.ts             список встроенных кейсов: id, подпись, статический import JSON
├─ events-view.tsx      клиент: выделение, переключатели, разделы
├─ flow-strip.tsx, figures-table.tsx, composition-bars.tsx

components/shared/sources-body.tsx    вынесено из figure-sources.tsx
components/shell/sidebar.tsx          пункт Events
```

Модель `explainCase` (имена уточняются в шаге 1):

- `report` — отчёт с решениями; `asComputed` — `runCase(input)`, то есть вывод CLI;
- `events[]` — каждая строка входа (номер строки — её адрес, у копий id одинаковый): запись, отпечаток содержания, судьба: `selected` (`inFigures`), `duplicate` (копия какой строки), `superseded` (какой версией), `candidate` (код спора), `rejected` (каким решением);
- `payments[]` — так же; вид денег: `received` (вилла, месяц), `held`, `unmatched`, `duplicate`, `conflicting`, `rejected`;
- `reservations[]` — версии по порядку, снимок, строки ночей из `ReservationDecision.nights`, платежи, коды;
- `cells` — для каждой клетки `by_property`, `monthly` и `total` список вкладов (ночь или платёж) с суммой; owner estimate — формула из клеток;
- `controls` — контрольные суммы событий и платежей (3.1);
- `cases[]` — спорные случаи: ключ, код, кандидаты, влияние каждого варианта; `decisions` — применённые и устаревшие.

Разделение как на `/import/data-quality`: всё, что считает и сверяет, — в `lib/nightly` (строгий lint без дробей, покрытие 100 %); подписи, цвета и раскладка календаря — `components/events/view-of.ts`. Модель уходит в клиент через `toView`, `bigint` в ней нет.

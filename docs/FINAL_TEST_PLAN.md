# План: комиссия по ночам и защита от повторного импорта

Финальное задание ([ТЗ](../final-test/ТЗ_КАНДИДАТУ.md)). Статус: v1.4 от 2026-10-23 — решения раздела 4 приняты Юрием, фазы 0–4 выполнены. Бюджет ТЗ — 2–3 часа активной работы; план рассчитан на **2 ч 40 мин**. Таблица факта — раздел 8.

## 1. Вывод

Делаем **небольшой отдельный модуль** `lib/nightly/` и CLI к нему. Модуль берёт из `lib/calc` готовые примитивы (деньги в `bigint`, ставка-дробь, `roundDiv`, `allocate`, календарь, `toView`) и добавляет только то, чего в ядре нет: разбор JSON-кейса, выбор актуального снимка брони, комиссию по ночам, помесячный отчёт по схеме ТЗ. Конвейер CSV → DQ → дашборд не трогаем.

Почему не встраиваем в ядро. Три решения ядра расходятся с ТЗ, и они не ошибки, а зафиксированные в журнале решения прошлого задания:

| Тема | Ядро сейчас | ТЗ | Что делаем |
|---|---|---|---|
| Ставка комиссии | одна на бронь, на дату заезда; смена ставки внутри проживания — флаг DQ-17 | по ставке **каждой ночи** (п. 4, B) | в `lib/nightly`: `commissionRulesOn` на дату каждой ночи |
| Округление комиссии | один раз на бронь, затем деление по ночам | **отдельно по каждой ночи**, HALF_UP (п. 6) | `applyRate(ночь, ставка, 'half-up')` на каждую ночь; `(a·bps + 5000) // 10000` — это ровно `roundDiv(a·bps, 10000, 'half-up')` |
| Версии брони | один `reservation_id`, разное содержание — случай `decide`, решает человек (DQ-02) | берётся **последний снимок** по `updated_at` автоматически (п. 10); спорно только равное `updated_at` (п. 14) | своя функция выбора снимка; DQ-02 не используем |
| Платёж | обязателен `property_id`, статуса нет | `property_id` нет, есть `status` (`received` / `pending`) | свои входные типы; вилла платежа — через бронь |
| Состав брони | `gross`, `ota_fee`, `refund`, `channel` | `accommodation_gross_idr`, `pbjt_idr`, `ota_fee_idr`; возвратов и канала нет | свои типы; PBJT — отдельная сумма, не доход |
| Пересечение правил комиссии | побеждает более поздняя `effective_from` (DQ-22 помечает) | «не придумывай правило» (п. 14) | строже: на ночь ровно одно правило, иначе исключение |

Переделка ядра под это — 5–8 часов (типы входа, `reservation.ts`, DQ-02/05/17, адаптер `lib/data`, 602 теста при пороге покрытия 100 %). Адаптер — 2.5 часа, и ТЗ прямо разрешает его (раздел 4, E). Перенос в ядро описываем в `IMPLEMENTATION_NOTES.md` как следующий шаг, не делаем.

Что ТЗ просит **не делать**: дашборд, UI, Postgres, Docker, деплой. Не делаем.

## 3. Структура модуля

```
lib/nightly/
├─ index.ts        публичный API: runCase(input: unknown): Report
├─ types.ts        Exception, ExceptionCode, Dedup — формы, общие для snapshots / fees / report
├─ schema.ts       zod: CaseInput по case_public.json; number → bigint через fromSafeInteger
├─ snapshots.ts    события → снимки броней; платежи без дублей; счётчики dedup; исключения
├─ fees.ts         снимок → строки ночей: ставка и комиссия на каждую ночь
├─ report.ts       ночи + платежи → monthly / total / by_property / cash_* / dedup / exceptions / trace
├─ testing/fixtures.ts  сырые (JSON-образные) записи для тестов: виллы и правила публичного кейса
└─ *.test.ts       тест рядом с каждым файлом + golden.test.ts на case_public.json + cli.test.ts (CLI, тест E)
scripts/nightly.ts CLI: npm run nightly -- <in.json> <out.json>
final-test/results_public.json   результат CLI, коммитится
IMPLEMENTATION_NOTES.md          до одной страницы, корень репозитория
```

Поток: `schema.parse` → `selectSnapshots` → `nightLines` на каждый принятый снимок → `buildReport` → `toView` → JSON с отсортированными ключами. Текущей даты в модуле нет: результат зависит только от входа.

### 3.1 Снимки и дубли (`snapshots.ts`)

События бронирования:
1. Группа по `source_event_id`. Все копии одинаковы по содержанию (сравнение канонического JSON события) → одна остаётся, остальные в `dedup.reservation_event_duplicates`. Разное содержание под одним `source_event_id` → исключение `CONFLICTING_EVENT`, бронь на `hold`.
2. Группа по `reservation_id`, снимок с наибольшим `updated_at`. Остальные → `dedup.superseded_reservation_versions`, их `source_event_id` перечисляются в `trace`. Два снимка с одинаковым наибольшим `updated_at` и разным содержанием → `AMBIGUOUS_VERSION`, `hold` (п. 14).
3. Проверки снимка, каждая — исключение с `hold`: вилла не в `properties` → `UNKNOWN_PROPERTY`; `currency ≠ base_currency` → `CURRENCY_MISMATCH` (п. 12); `check_out ≤ check_in` → `INVALID_STAY`; статус не из `confirmed | modified` → `UNKNOWN_STATUS`, в том числе `cancelled` (в ТЗ статуса нет; решение в разделе 4, п. 4).

Платежи:
1. Группа по `payment_id`: одинаковые → один остаётся, остальные в `dedup.payment_duplicates`; разные → `CONFLICTING_PAYMENT`, `hold`.
2. `status = pending` → не деньги (п. 11): в `cash_held_idr`, исключение `PENDING_PAYMENT`. Статус не из `received | pending` → `UNKNOWN_STATUS`, `hold`.
3. `received`, `reservation_id` не найден среди снимков → `UNMATCHED_PAYMENT`, в `cash_unmatched_idr` (п. 13). Найден, но бронь на `hold` → `PAYMENT_HELD`, в `cash_held_idr`. Иначе — поступление виллы брони в месяц `payment_date`.

### 3.2 Комиссия по ночам (`fees.ts`)

На снимок: `nights = eachNight(check_in, check_out)`; `allocate(accommodation, nights)`, `allocate(pbjt, nights)`, `allocate(ota_fee, nights)`; на каждую ночь ровно одно правило виллы, действующее в эту дату (0 → `NO_COMMISSION_RULE`, >1 → `AMBIGUOUS_COMMISSION_RULE`, оба `hold` на всю бронь; коды в порядке ночей, каждый один раз); `fee = applyRate(nightGross, rateFromBps(bps), 'half-up')`. Строка ночи: дата, месяц, три суммы, `rate_bps`, комиссия.

`nightLines` вызывается из `selectSnapshots` сразу после проверок снимка и **до** размещения платежей: иначе платёж брони, задержанной из-за ставки, уже лежал бы в `cash_received`, а по решению 4.3 ему место в `cash_held` (`PAYMENT_HELD`). Принятое решение по брони несёт свои строки ночей (`nights`), отчёту остаётся их сложить.

### 3.3 Отчёт (`report.ts`)

Шесть показателей на месяц: `accommodation_gross_idr`, `pbjt_liability_idr`, `ota_fee_idr`, `management_fee_idr` — суммы строк ночей с датой в месяце; `owner_estimate_idr = accommodation − ota_fee − management_fee` (п. 8); `cash_received_idr` — платежи `received` принятых броней по `payment_date`. `monthly` — по `report_months`; `total` — сумма по тем же месяцам; `by_property` — то же по каждой вилле из `properties`, включая нулевые. Ночь или платёж вне `report_months` → исключение `OUTSIDE_REPORT_MONTHS`, в `total` не входит (чтобы `total = Σ monthly`; решение в разделе 4, п. 2). `trace` — по **каждой** брони: выбранный `source_event_id`, вытесненные версии, ночей, разбивка по месяцам с `rate_bps`; R101 в их числе. Массивы отсортированы по ключам, JSON стабилен между запусками.

Принято в фазе 3:

- Строка `trace` на бронь: `selected_source_event_id` (выбранная версия или та, что не прошла проверки; `null`, когда версию выбрать нельзя — `CONFLICTING_EVENT`, `AMBIGUOUS_VERSION`), `superseded_source_event_ids`, `hold`, `nights` (начисленных ночей; 0 у брони на `hold`), `monthly` — по каждому месяцу ночей, в окне или нет: `nights`, `rate_bps` (список разных ставок месяца в порядке ночей — одна, если правило не менялось внутри месяца), `accommodation_gross_idr`, `management_fee_idr`. Три ключа из `output_schema.json` сохранены, два добавлены.
- `cash_held_idr` и `cash_unmatched_idr` — не показатели периода: в них входит каждый задержанный или непривязанный платёж независимо от даты, без `OUTSIDE_REPORT_MONTHS`; окно проверяется только там, где деньги кладутся в месяц (ночи принятых броней, полученные платежи принятых броней). Иначе деньги вне окна исчезли бы из вывода совсем.
- `exceptions` — один список: брони по id, затем платежи по id; коды одной записи в порядке проверок, `OUTSIDE_REPORT_MONTHS` последним. `by_property` — все виллы из `properties`, месяцы — все из `report_months`, нули там, где движения нет; `owner_estimate_idr` не обрезается снизу.
- Сетка вилла × месяц — основа: `monthly` — её сумма по виллам, `total` — по месяцам; сходимость по построению, golden проверяет её ещё раз числами.
- `runCase` возвращает уже `toView`-представление (числа); `formatReport` — текст CLI: ключи отсортированы на каждом уровне, отступ в два пробела, перевод строки в конце. Один вход — одни байты; проверено перестановкой всех пяти массивов входа.

### 3.4 CLI (`scripts/nightly.ts`)

Принято в фазе 4:

- `npm run nightly -- <case.json> <results.json>`: читает файл, `runCase`, пишет `formatReport`; каталог результата создаётся, если его нет. На stdout одна строка: путь, `case_id`, число исключений, три счётчика `dedup`. `results_public.json` сверяется с выводом CLI байт в байт в `cli.test.ts`; тот же тест напоминает перегенерировать файл после изменения модуля.
- Коды выхода: 0 — записано; 1 — файл не читается, не JSON или не кейс ожидаемого формата (ошибки схемы печатает `z.prettifyError`, все сразу, каждая с путём к полю: `reservation_events[2].accommodation_gross_idr`); 2 — неверный вызов (нет двух путей или передана опция). При ошибке файл результата не пишется. Исключение не из zod — дефект, не плохой вход: падает со стеком.
- Тест E — копия публичного кейса в памяти, не файлом: декабрьская ставка 2200 → комиссия R101 = 374 000 + 484 000, ноябрь и деньги не меняются; E_R101_V3 с более поздним `updated_at` (те же даты, 4 800 000 / 480 000 / 720 000) → выбрана она, `superseded = 2`, оба месяца считаются по её суммам, те же три исключения; позиция новой версии во входе не важна. Оба изменения вместе прогоняются через CLI во временный каталог: байты равны `formatReport(runCase(…))`, декабрь R101 — 2 ночи × 1 200 000 × 22 % = 528 000.

## 4. Решения по неоднозначностям

Вопросов Ирине не задаём: решаем сами, опираясь на текст ТЗ, и каждое решение записываем одной строкой с причиной в `IMPLEMENTATION_NOTES.md`:

1. **`cash_held_idr`** есть в `output_schema.json`, но не описан в тексте ТЗ. Принимаем: `pending`-платежи + полученные платежи броней на `hold` — деньги, о которых знаем, но к результату виллы пока не относим (п. 11 и раздел 4 D ТЗ: не прятать неподтверждённые деньги). На публичном кейсе это 50 000 (P303). Отвергнуто: только `pending` — платежам броней на `hold` тогда негде лежать, кроме `cash_received_idr` или `cash_unmatched_idr`, и оба неверны.
2. **`total`** — сумма по `report_months`, не по всем данным. Период в ТЗ задан только месяцами (п. 4A: «для 2026-11, 2026-12 и всего периода»), и итоговая строка обязана сходиться со строками месяцев и с `by_property`. Ночь или платёж вне окна в итог не входят, но видны: исключение `OUTSIDE_REPORT_MONTHS`, ночи ещё и в `trace`. Бронь на границе окна режется по ночам (п. 7), а не держится целиком; аванс вне окна за ночи внутри окна — деньги своего месяца, в итог не входит. Отвергнуто: итог по всем данным (не сходится с месяцами, разницу ничто не объясняет) и месяцы из данных вместо `report_months` (меняет форму вывода: лишние ключи в `monthly` и `by_property`). На публичном кейсе все варианты дают одни числа.
3. **Платёж брони с `CURRENCY_MISMATCH`** (и любой другой брони на `hold`) — в `cash_held_idr`, не в `cash_received_idr`; исключение `PAYMENT_HELD`. Деньги реальные, но вилле не подтверждены: иначе у виллы появится кэш без начисления по записи, которую мы же пометили ошибочной. `cash_unmatched_idr` не подходит: п. 13 определяет его как «бронь не найдена», а здесь она найдена.
4. **Статус `cancelled`** в ТЗ не упомянут → незнакомый статус по п. 14: `UNKNOWN_STATUS`, бронь на `hold`, её платёж — в `cash_held_idr` (`PAYMENT_HELD`). Принимаются только `confirmed | modified`. Отвергнуто: начисления 0 и платёж как поступление (так ведёт себя дашборд) — для теста важнее не придумывать правило.
5. **`action`** в исключениях — одно значение `hold`, как в примере `output_schema.json`: каждая запись в `exceptions` означает, что сумма не вошла в подтверждённые итоги (`pending`-платёж, платёж или ночь вне окна, USD-бронь, платёж на несуществующую бронь). Отвергнуто: `info` / `review` — классификация, которую ТЗ не просит.
6. Две версии с одинаковым `updated_at` и одинаковым содержанием под разными `source_event_id` — одна версия: берём меньший `source_event_id` (детерминированно, не по порядку во входе), вторую считаем вытесненной в `dedup` и показываем в `trace`, без исключения; цифры от выбора не зависят. Одинаковый `updated_at` с **разным** содержанием → `AMBIGUOUS_VERSION`, `hold` (п. 14).

Принято в фазе 1 (не покрыто пунктами выше; на публичном кейсе ни одно не срабатывает):

7. **Ошибка формата против исключения.** Отрицательная или дробная сумма, число вне безопасного диапазона, дата вроде `2026-02-30`, `updated_at` без зоны, `rate_bps` вне 0–10000, `effective_to` раньше `effective_from`, повтор месяца в `report_months` или виллы в `properties` — ошибка формата всего файла (код выхода 1, путь к полю), не исключение на записи: п. 1 ТЗ определяет корректную сумму как целые рупии, формула п. 6 задана для неотрицательных. Статус и валюта — свободный текст: незнакомое значение — исключение на записи (п. 14), файл читается. Отсутствующий или `null` `effective_to` — правило без конца, как читает `commissionRulesOn`.
8. **`updated_at`** хранится как момент времени (миллисекунды эпохи), не как строка: `…T09:00:00Z` и `…T13:00:00+04:00` — одна версия, а строковое сравнение ставит `…00Z` позже `…00.500Z`. Доли миллисекунды отбрасываются: версии, различающиеся только ими, считаются одновременными — при разном содержании `AMBIGUOUS_VERSION`, безопасная сторона.
9. **Вилла с `base_currency ≠ IDR`** — её брони `CURRENCY_MISMATCH`, даже если валюта брони совпадает с базовой: отчёт в рупиях, поля `_idr`, пересчёта нет (п. 12). Отвергнуто: ошибка формата — ломает весь запуск из-за одной виллы.
10. **`CONFLICTING_EVENT`** держит всю бронь, даже если есть чистая более поздняя версия: лента событий по ней недостоверна. Пишется на бронь (`record_type: reservation`, `record_id` = `reservation_id`), как в примере `output_schema.json`; конфликтное событие с двумя `reservation_id` держит обе. Проверки снимка (вилла, валюта, даты, статус) — только у выбранной версии: USD в старой версии, исправленный в новой, — бронь принята (п. 10).
11. **Платежи, не описанные в 3.1.** `CONFLICTING_PAYMENT` (один `payment_id`, разные суммы) — ни в один из `cash_*`: единой суммы нет, выбрать одну значило бы придумать правило; виден в `exceptions`. Незнакомый статус — `cash_held_idr` с `UNKNOWN_STATUS`: сумма известна, подтверждения нет. `pending` для несуществующей брони — только `PENDING_PAYMENT`, в `cash_held_idr`: статус проверяется первым, п. 13 говорит о полученных платежах.
